# 写作示例与证据细节

本文件补充 [核心规则](../SKILL.md)，按需要查阅。示例中的技术名词和数字用于解释写法，不是其他项目应沿用的配置或实验结果。

## 连贯解释机制

先建立读者需要的背景，再引出动作和原因。例如解释融合，先说明原有步骤如何产生、存储和读取中间结果，再讲新实现如何直接使用这些结果，最后用少了多少读写解释可能的收益。不要先抛出一个自创优化名，再默认读者理解它包含的全部步骤。

| 含糊写法 | 应补充的具体过程 |
| --- | --- |
| “Fixpipe 是矩阵乘的输出通路” | 矩阵乘得到 INT32 结果后，硬件在写入显存时乘权重 scale（缩放系数）并转成 FP16；随后解释当前实现如何恢复每个 token 的缩放系数。 |
| “一个整数核完成请求索引” | 一次算子调用按请求编号查找 KV 缓存位置、换算页号，并完成页表尾部清零和请求长度复制；避免把软件算子说成硬件核。 |
| “系数折叠减少逐元素计算” | 把一个 token 共用的归一化系数放进量化的缩放系数，说明原来逐元素进行的哪次乘法因此被省去。 |
| “矩阵计算和向量准备重叠” | 说明各块包含哪些 token/通道，准备产生什么数据，以及缓冲区何时可读、何时可覆盖，由此解释哪些操作能同时进行。 |
| “NZ 是硬件友好的布局” | 给出当前实现的块尺寸、块内与块间元素顺序、转置方向；分清逻辑形状与实际存储。 |
| “完整单层消费链加速” | 列出计时覆盖的实际步骤，如 QKV 投影、注意力、门控与输出投影；自行拼接的步骤不能自动称为实际模型完整层。 |

使用表中的术语前，仍须按读者需要介绍其作用。相同的启动 grid（算子任务网格）缩小机制可合并讲，表格只列各应用的必要差异。项目已经固定的数据类型与布局不必在每项优化中重复，但解释数据流所需的信息应保留。

## 正向陈述

直接从事实、机制或正确做法开始，尽量不要使用“不是……而是……”“××不对”等否定或纠错口吻，省去假设性的错误观点和反驳。

例如，已知计时仅覆盖 QKV 模块时，可将“这种理解不对，测到的只是模块耗时”写为“本次计时覆盖 QKV 模块，结果表示该模块的耗时”。

## 性能结果的完整表达

不要只写“快了 20%”。下面是表达示例，数字为假设：

> 在同一设备、相同输入下，基线关闭本次评估的所有优化，实验组仅开启归一化与量化融合。独立脚本只计这两个步骤的总耗时；两组均预热 20 次、重复计时 100 次。中位耗时从 10 ms 降到 8 ms，减少 20%，加速比为 1.25 倍。这组结果未测完整服务。

实际报告应给出影响主要结论的设备、版本、输入规模等具体条件，不用“同一设备”代替必要信息。共用条件集中说明一次，各组只补充影响比较的差异，不重复罗列完整环境；不影响理解和比较的环境细节不展开。后文不反复加“不能代表整体”的声明。若只测单次迭代，即使重复了许多次，也要明确该范围。

只在读者确实需要核查某项关键结果时，链接已有记录，或补充必要的代码版本、命令与参数；不为每个数据点建立复现清单，也不默认新增环境附录或汇总全部日志。必要信息缺失时如实说明，不把无法核查的结果写成已经复现，也不为补齐文档自行重跑实验。

设基线耗时为 `T₀`、优化后为 `T₁`，耗时减少比例为 `(T₀−T₁)/T₀`，加速比为 `T₀/T₁`。吞吐增加比例使用基线吞吐作分母，不能和耗时减少比例混用。直接写“耗时增加 2.5%”，不要写“耗时减少 −2.5%”。

对依赖其他优化的项目，主对照仍是“全部关闭”与“仅开启该项及必需依赖”，并列明依赖带来的配置差异。这只能支持这一组合的效果；若另测“仅依赖”与“依赖加该项”，其结果才说明该项在依赖之上的增量，须单独标注。

主报告直接放入关键数据。展示数据时强烈建议用折线图呈现趋势与对比；多个输入规模优先用优化前后两条折线比较，明确标注横轴、纵轴分别代表的变量及单位。例如横轴为每卡实际 token 数，纵轴为模块耗时（ms），图内副标题可写“QKV 模块｜单次 iteration｜独立脚本”；若测的是实际服务中的完整请求，可写“完整请求耗时｜实际服务”。按实际情况标注，详细配置与统计方式放在图外的图注或正文中。服务吞吐应单独标明服务测试条件，不能与模块耗时混成同一条趋势。单点结果用表格或柱状图即可。

选图应抓住实验最核心的结论，避免为同一实验机械地画四张图再拼成一张。若 prefill 与 decode 分别回答不同阶段的核心性能问题，可以各保留一图或一个分面。图内保留必要标签、图例、简短的计时范围与测量场景标注；实验细节、原因分析和长解释放在图外的图注或正文中，让读者容易看清曲线与比较关系。

## 最终图表检查

在实际交付的页面或文件中检查，不只看绘图窗口里的放大预览：

- 以最终阅读尺寸检查坐标轴、单位、图例、计时信息和关键标注；文字与线条清楚，无遮挡、裁切或字体缺失。导出后重新查看实际文件。
- 同一组图中的字体、基线与优化后配置的名称和视觉表示保持一致。图、表与正文的单位、工作量和关键数字一致，不能混用旧图与新数据。
- 不只靠颜色区分配置，同时使用线型、点形或直接标签；必要时检查灰度下是否仍能区分。
- 为静态报告选择清晰的导出格式，可使用适合载体的矢量图或足够分辨率的位图，不用截图代替可正常导出的原图。不规定所有项目使用同一格式或固定 DPI。
- 交互图需要进入静态报告或导出文件时，提供同一数据、同一条件下的静态版本；关键结论不能依赖悬停或点击才能读到。

## 读者问题检查

根据实际读者和文档目的选取问题，不强制每篇报告回答同一套问题。例如：

- 原来遇到了什么问题，为什么需要改变？
- 谁处理什么数据，做了什么，结果交给谁？
- 前文提出的关键问题在哪里得到回答，尚未解决的部分是什么？
- 方案选择由哪些约束和证据支持，读者需要知道哪些代价？
- 关键数字比较的是谁、测量了哪部分，能支持多强的结论？

只使用成稿和其中实际可访问的引用回答，并定位支持答案的位置。依赖聊天内容、没有定义的术语或未说明的前提才能回答时，补回必要背景；正文缺少核心结果时，仍须在正文补齐，不能让读者只靠追查日志理解结论。

普通修改做自查，不逐节增加问答、评分或反复确认。重要长文需要独立检查时，让没有聊天上下文的读者或独立会话仅凭文档与引用回答问题，指出歧义、矛盾和隐含前提；根据实际发现修订。没有进行独立检查时如实称为自查，不声称通过独立读者测试；阅读理解检查不能替代技术核实或实验验证。

## 证据的细节

| 事实来源 | 正确处理 |
| --- | --- |
| 接口或硬件资源的实际要求 | 解释与机制有关的布局、数据或缓存要求，无需逐项复制实现检查。 |
| 仅覆盖若干输入 | 写清已测范围，不把未测点写成退化或算法不适用。 |
| 某些输入反复测到更慢 | 保留实际慢点、比较范围和重复结果；不为偶然波动编造硬件原理或新分支。 |

- 独立随机输入、重复计时和一次图捕获是不同统计单位，不互相替代。A/A 指相同计算的重复对照，用于观察波动；收益接近波动时，不能声称已证明稳定加速。
- 区分源码确认的机制、近似模型、实验趋势与已证明结论。保留实际误差、显存副本等成本、未做的质量评估与部署限制，用事实代替笼统免责声明。
- “逐位一致”必须有精确比较；存在浮点误差时给出误差指标及比较对象，不从张量相对误差推算模型质量下降比例。影响结论的舍入点应写在对应步骤。
- 推理用 token/请求、训练用样本/step、通信用字节/rank、存储用记录/块等项目单位；解释其范围，分清每卡/全局和实际/补齐。不要机械套用其他领域的数量与结论。
- 历史实验保留当时源码与配置；缺少当前版本的完整服务测试时，不能把旧数据改名为新成绩。写作审查不自行更改算法、分流条件或扩大硬件测试。

## 用公式解释成本

只在能帮助读者理解时使用公式，避免为显然的动作强加推导。例如：

- **融合读写**：每次处理 `N` 个 token，每个向量含 `D` 个 BF16 数值，中间结果为 `2ND` 字节。量化直接使用片上结果，便可少从显存读取这 `2ND` 字节；若仍写出中间结果，就不能把这次写入也算作节省。
- **分块流水**：`n` 个块，每块矩阵计算耗时 `c`、向量准备耗时 `v`，两者使用相同时间单位。串行约需 `n(c+v)`；在各块成本相同、两阶段可理想重叠的模型下，约需 `c+v+(n−1)max(c,v)`，再加实际同步开销。这解释了重叠减少等待，以及较慢阶段如何限制收益。

成本估算使用近似关系，注明影响结论的假设。无需附加“公式不是无限精度”“不构成性能保证”等泛泛声明，也不能把经验门槛伪装成公式的精确结论。
